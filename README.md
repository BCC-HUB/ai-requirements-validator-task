# reqvalidator — ИИ-агент проверки требований

[![CI](https://github.com/azekowka/ai-requirements-validator-task/actions/workflows/ci.yml/badge.svg)](https://github.com/azekowka/ai-requirements-validator-task/actions/workflows/ci.yml)

Агент проводит **статическую проверку документа требований до разработки**: читает документ
(PDF, DOCX, Markdown, TXT, HTML), выделяет отдельные требования, проверяет каждое требование и
набор целиком по критериям **ISO/IEC/IEEE 29148:2018 (п. 5.2.5, 5.2.6, 5.2.7)** и
**IEEE Std 830-1998 (п. 4.3)** и записывает отчёт на русском языке.

Решение задачи хакатона **BCC-HUB x MNU FinTech Hackathon** — условие в [`docs/TASK.md`](docs/TASK.md).

| Что сдаётся | Где |
| :--- | :--- |
| Агент (код, зависимости, инструкция) | этот репозиторий: [`reqvalidator/`](reqvalidator), [`requirements.txt`](requirements.txt) |
| Проверенный документ (выдан организаторами) | [`docs/requirements.md`](docs/requirements.md) |
| Отчёт, сформированный агентом по этому документу | [`reports/requirements-report.md`](reports/requirements-report.md) (+ [JSON](reports/requirements-report.json)) |

## Результат проверки документа из задания

Отчёт [`reports/requirements-report.md`](reports/requirements-report.md) получен одной командой

```bash
python -m reqvalidator docs/requirements.md reports/requirements-report.md --provider claude-cli --model claude-opus-5-5
```

| Паспорт прогона | |
| :--- | :--- |
| Модель | Claude Opus 5.5 (`claude-opus-5-5`, effort high) через Claude Code CLI |
| Версия агента | 1.0.0, коммит [`35ad78b`](https://github.com/azekowka/ai-requirements-validator-task/commit/35ad78b) |
| Прогон | 25.11.2026, 12 мин, 16 обращений к модели, без ошибок и предупреждений |

**Что нашёл агент:** выделено **55 требований** (идентификатор в документе есть у 18), подтверждено
**90 замечаний** — 🔴 5 критичных, 🟠 60 существенных, 🟡 25 незначительных; критерии приёмки
покрывают 12 % проверяемых требований. **Итог: начинать разработку и тестирование нельзя.**

Критичные дефекты:

1. Критерий приёмки о покупке на стыке месяцев противоречит Ф-2 (месяц по дате совершения покупки).
2. Лимит «один push в месяц» (Ф-3) противоречит правилу Ф-4 «независимо от истории».
3. Неверная сумма в API одновременно описана как ответ 200 с `ERROR` и как ответ 400.
4. Не описан контракт событий процессинга (возвраты, отмены, переводы, момент проведения).
5. В части B нет метода чтения настроек и суммы за месяц, хотя часть A и UI на него опираются.

**Как читать отчёт.** Раздел 7 «Итог» — вывод и список «что исправить в первую очередь»;
раздел 6 — сводка и таблица критичных дефектов; раздел 4 — разбор каждого требования с цитатой,
местом в документе (строка) и предлагаемой формулировкой; раздел 5 — проблемы набора в целом
(противоречия, пропуски, покрытие критериями приёмки). Все ID замечаний (`Д-…`) и требований
(`ТР-…`) кликабельны.

**Проверено вживую** (помимо автотестов):

* Claude Opus 5.5 через Claude Code CLI — итоговый отчёт выше.
* Google Gemini на бесплатном ключе — прогон документа из задания (51 требование, 76 замечаний, 12,5 мин)
  и PDF-версии учебного документа. Во время пикового спроса Google `gemini-flash-latest` отвечала 503,
  и агент продолжил на `gemini-3.5-flash`. В том прогоне перегружены оказались все модели сразу, и
  заключение было собрано без модели; после этого агент научился возвращаться к временно
  перегруженным моделям и ждать дольше (до ~3 мин).
* OpenRouter — запросы к Claude Sonnet 5.5 через ключ OpenRouter (прогон учебного документа).

## Быстрый старт

Нужен Python 3.10+.

```bash
git clone https://github.com/azekowka/ai-requirements-validator-task.git
cd ai-requirements-validator-task
python -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env                 # Windows: copy .env.example .env
# откройте .env и впишите GEMINI_API_KEY=<ваш ключ> (см. «Ключ LLM» ниже)

python -m reqvalidator docs/requirements.md reports/report.md
```

Отчёт появится в `reports/report.md`, рядом — машиночитаемая копия `reports/report.json`.
В консоли агент печатает ход этапов и итог: число требований, замечаний и вывод о готовности.

## Ключ LLM

Агент работает с любой из поддерживаемых моделей. Рекомендуемый бесплатный вариант — **Google Gemini**.

### Google Gemini (бесплатный тариф Google AI Studio)

1. Откройте <https://aistudio.google.com/apikey> и войдите аккаунтом Google.
2. Нажмите **Create API key** и скопируйте ключ.
3. Впишите его в файл `.env` в корне репозитория:

   ```dotenv
   LLM_PROVIDER=gemini
   GEMINI_API_KEY=ваш_ключ
   GEMINI_MODEL=gemini-flash-latest
   ```

`gemini-flash-latest` — алиас Google на актуальную модель Gemini Flash, он не устаревает при выходе
новых версий. Можно указать конкретную модель (например, `gemini-3.5-flash`); список моделей,
доступных вашему ключу: `python -m reqvalidator --list-models`.

Особенности бесплатного тарифа, которые агент учитывает сам:

* **Лимит запросов в минуту.** Запросы идут последовательно с паузой 4 с; после ответа 429 агент
  ждёт столько, сколько указал API, и повторяет запрос.
* **Перегрузка и снятые модели.** Если модель отвечает «high demand» (503), недоступна новым ключам
  (404) или исчерпала дневную квоту, прогон продолжается на резервной модели
  (`gemini-flash-latest` → `gemini-3.5-flash` → `gemini-flash-lite-latest`, список меняется
  переменной `LLM_FALLBACK_MODELS`). Переключение записывается в паспорт отчёта.
* Прогон документа из задания — около 15–20 запросов и 10–20 минут.

### Другие провайдеры

| Провайдер | `LLM_PROVIDER` | Ключ в `.env` | Модель (по умолчанию) | Примечание |
| :--- | :--- | :--- | :--- | :--- |
| Google Gemini | `gemini` | `GEMINI_API_KEY` | `GEMINI_MODEL` (`gemini-flash-latest`) | бесплатный тариф |
| Anthropic Claude | `anthropic` | `ANTHROPIC_API_KEY` или `CLAUDE_API_KEY` | `ANTHROPIC_MODEL` (`claude-opus-5-5`) | `pip install anthropic` |
| OpenRouter | `openrouter` | `OPENROUTER_API_KEY` | `OPENROUTER_MODEL` (`anthropic/claude-opus-5.5`) | один ключ к Claude, Gemini, DeepSeek, GPT |
| DeepSeek | `deepseek` | `DEEPSEEK_API_KEY` | `DEEPSEEK_MODEL` (`deepseek-v4-pro`) | или `deepseek-flash` |
| OpenAI и совместимые (vLLM, LM Studio) | `openai` | `OPENAI_API_KEY` | `OPENAI_MODEL` (`gpt-4o-mini`) | адрес — `OPENAI_BASE_URL` |
| Ollama (локально) | `ollama` | не нужен | `OLLAMA_MODEL` (`qwen2.5-coder:7b`) | контекст — `OLLAMA_NUM_CTX` |
| Claude Code CLI | `claude-cli` | не нужен (вход в Claude Code) | `CLAUDE_CLI_MODEL` (модель Claude Code) | `claude -p` без инструментов |

Если `LLM_PROVIDER` не задан, агент берёт первый найденный ключ в порядке Gemini → Claude →
OpenRouter → DeepSeek → OpenAI → Ollama, так что достаточно вписать в `.env` один ключ; модель
указывать не обязательно. Провайдер и модель можно переопределить флагами:
`--provider openrouter --model google/gemini-3.5-flash`.
Ключи хранятся только в `.env` (он в `.gitignore`); в репозитории лежит пример без ключа — [`.env.example`](.env.example).

## Запуск

```bash
python -m reqvalidator <файл требований> [<файл отчёта>] [опции]
```

* `<файл требований>` — `.pdf`, `.docx`, `.md`, `.txt`, `.html`.
* `<файл отчёта>` — путь к Markdown-отчёту (по умолчанию `reports/<имя документа>-report.md`).
  JSON с полными результатами пишется рядом (`--json PATH` — другой путь, `--no-json` — не писать).
  Если указать файл с расширением `.json`, агент запишет только JSON.

После `pip install -e .` доступна и короткая команда `reqvalidator docs/requirements.md reports/report.md`.

| Опция | Назначение |
| :--- | :--- |
| `--provider`, `--model` | выбрать провайдера и модель вместо значений из `.env` |
| `--effort low…max` | глубина рассуждений для `anthropic`, `openrouter` и `claude-cli` |
| `--batch-size N` | сколько требований проверять в одном запросе (по умолчанию 6) |
| `--concurrency N` | параллельных запросов (Gemini — 1, остальные — 4) |
| `--no-review` | пропустить этап самопроверки замечаний |
| `--no-cache` | не использовать кэш ответов модели (`.reqvalidator_cache/`) |
| `--env-file PATH` | другой файл настроек вместо `./.env` |
| `--list-models` | вывести модели, доступные ключу |
| `-v` / `-q` | подробный журнал / только итог |

Коды завершения: `0` — отчёт записан, `2` — ошибка настройки (нет ключа и т. п.), `3` — документ
не прочитан, `4` — модель недоступна, `1` — прочее. Все параметры `.env` перечислены в
[`.env.example`](.env.example).

**Повторяемость.** Ответы модели кэшируются по хешу промпта: повторный прогон того же документа с
той же моделью и версией агента воспроизводит результат без новых запросов. Для «чистого» прогона
используйте `--no-cache`.

### Запуск в GitHub Actions (без локальной установки)

В репозитории есть ручной workflow [`Generate report`](.github/workflows/generate-report.yml):

1. Settings → Environments → создайте окружение и добавьте в **Environment secrets** хотя бы один ключ:
   `GEMINI_API_KEY`, `CLAUDE_API_KEY`, `OPENROUTER_API_KEY` или `DEEPSEEK_API_KEY`.
2. Actions → **Generate report** → **Run workflow**: укажите имя окружения, провайдера и (необязательно)
   модель и путь к документу.
3. Готовый отчёт (`.md` и `.json`) скачивается со страницы запуска, артефакт `requirements-report`.

## Как работает агент

```text
документ ─► чтение и нумерация строк ─► статические проверки (без LLM)
         ─► LLM: нарезка на требования ─► проверка покрытия строк ─► LLM: дорезка пропущенного
         ─► LLM: проверка каждого требования по И1–И9 (пакетами, параллельно)
         ─► LLM: проверка набора — согласованность │ полнота и покрытие приёмкой │ структура
         ─► сверка всех цитат с текстом документа ─► LLM: самопроверка замечаний
         ─► правила готовности ─► LLM: обоснование и приоритеты ─► отчёт .md + .json
```

1. **Чтение.** Любой формат приводится к пронумерованным строкам; у каждой строки есть «адрес» —
   строка Markdown/TXT, страница и строка PDF, абзац или строка таблицы DOCX. PDF разбирается через
   pdfplumber: таблицы — построчно, заголовки — по кеглю и начертанию, колонтитулы и номера страниц
   удаляются.
2. **Статические проверки** (`reqvalidator/lint.py`) находят размытые слова и открытые перечни
   (ISO/IEC/IEEE 29148, п. 5.2.7), заглушки (`TBD`, «заполняются»), незаполненные варианты шаблона
   («Да / Нет»), пустые разделы и строки таблиц, смешение единиц (тиыны и тенге), `GET` для
   изменения данных. Сигналы передаются модели как подсказки и выводятся в приложении отчёта.
3. **Нарезка.** Модель выделяет требования с дословной цитатой и идентификатором документа (если он
   есть). Агент ищет каждую цитату в тексте; строки, не вошедшие ни в требование, ни в исключения,
   отправляет модели повторно, а остаток явно фиксирует в отчёте.
4. **Проверка каждого требования** по критериям И1–И9: модель заполняет чек-лист по всем критериям,
   по каждому нарушению даёт описание, цитату, связанные места и рекомендацию, а также предлагает
   улучшенную формулировку. Весь документ передаётся как контекст, поэтому находятся противоречия с
   другими разделами и критериями приёмки.
5. **Проверка набора** — три отдельных прохода: согласованность, осуществимость и понятность
   (Н2–Н4); полнота и возможность валидации с матрицей покрытия требований критериями приёмки
   (Н1, Н5); ранжирование, модифицируемость и прослеживаемость (Н6–Н8).
6. **Привязка к тексту.** Каждая цитата модели сверяется с документом (точный, «с пропусками» и
   нечёткий поиск). Номера строк и страниц в отчёте вычисляет агент, а не модель. Замечание к набору
   без найденной цитаты в основной отчёт не попадает.
7. **Самопроверка.** Модель-рецензент отсеивает ложные срабатывания, объединяет дубликаты и
   калибрует серьёзность; отклонённое показывается в приложении Б.
8. **Итог.** Готовность к разработке и тестированию определяют детерминированные правила по
   подтверждённым дефектам (раздел 7 отчёта), модель формулирует обоснование и список
   «что исправить в первую очередь» со ссылками на ID замечаний.

Устойчивость: повторы при 429/5xx/обрывах с экспоненциальной паузой, исправление невалидного JSON
повторным запросом с текстом ошибки, деление пакета пополам при обрезанном ответе, поштучная
проверка при сбое пакета, эвристическая нарезка, если модель не справилась с нарезкой.

### Критерии

| Код | Критерий | Источник |
| :--- | :--- | :--- |
| И1 | Необходимость | ISO/IEC/IEEE 29148, 5.2.5 a |
| И2 | Уместность (без лишних проектных решений) | 5.2.5 b |
| И3 | Однозначность | 5.2.5 c, 5.2.7; IEEE 830, 4.3.2 |
| И4 | Полнота | 5.2.5 d; IEEE 830, 4.3.3 |
| И5 | Единичность (атомарность) | 5.2.5 e |
| И6 | Осуществимость | 5.2.5 f |
| И7 | Проверяемость | 5.2.5 g; IEEE 830, 4.3.6 |
| И8 | Корректность и непротиворечивость | 5.2.5 h; IEEE 830, 4.3.1, 4.3.4 |
| И9 | Соответствие шаблону и стилю | 5.2.5 i, 5.2.8 |
| Н1 | Полнота набора | 5.2.6 a; IEEE 830, 4.3.3 |
| Н2 | Согласованность набора | 5.2.6 b; IEEE 830, 4.3.4 |
| Н3 | Осуществимость набора | 5.2.6 c |
| Н4 | Понятность набора | 5.2.6 d |
| Н5 | Возможность валидации | 5.2.6 e |
| Н6 | Ранжирование по важности и стабильности | IEEE 830, 4.3.5 |
| Н7 | Модифицируемость | IEEE 830, 4.3.7 |
| Н8 | Прослеживаемость | IEEE 830, 4.3.8; 29148, 5.2.8 |

### Состав отчёта

| Требование ТЗ | Раздел отчёта |
| :--- | :--- |
| Паспорт прогона: документ, дата, модель, версия агента (коммит) | 1. Паспорт прогона (+ SHA-256 файла, параметры, число запросов и токенов) |
| Как агент нарезал требования: ID в отчёте — ID в документе — формулировка, цитата | 3. Таблица нарезки с местом в документе и дословной цитатой; список исключённых фрагментов |
| Проверка каждого требования | 4. Матрица «требование × критерий» и разбор по каждому требованию с предлагаемой формулировкой |
| Проверка всего набора | 5. Оценка по Н1–Н8, замечания к набору, покрытие критериями приёмки |
| Сводка: число требований, нарушений, критичные дефекты | 6. Сводка; критичные дефекты сгруппированы: противоречивые, непроверяемые, неполные и прочие |
| Итог: можно ли начинать разработку и тестирование, что исправить первым | 7. Итог и приоритеты исправлений со ссылками на замечания |

Каждое замечание содержит ID (`Д-01`…), критерий, серьёзность, цитату с местом в документе и
рекомендацию.

## Структура репозитория

```text
reqvalidator/
  cli.py            командная строка
  config.py         настройки из .env и окружения
  loaders.py        чтение PDF / DOCX / MD / TXT / HTML
  document.py       модель документа, места, поиск цитат
  lint.py           детерминированные проверки текста
  criteria.py       каталог критериев и шкала серьёзности
  prompts.py        промпты этапов (на русском)
  pipeline.py       конвейер проверки
  report.py         отчёт Markdown / JSON
  models.py         модели данных и схемы ответов модели
  version.py        версия агента и коммит git для паспорта
  llm/              провайдеры: Gemini, Anthropic, OpenRouter, DeepSeek, OpenAI-совместимые, Ollama, Claude Code CLI
docs/               условие задачи и проверяемый документ
reports/            отчёт агента по docs/requirements.md
tests/              автотесты (детерминированная «модель» вместо LLM) и примеры документов
```

## Тесты

```bash
pip install -e ".[dev]"
ruff check reqvalidator tests
pytest -q
```

Тесты не требуют ключа: вместо LLM используется сценарная заглушка
([`tests/fakes.py`](tests/fakes.py)). Проверяются чтение всех форматов (включая PDF и DOCX), поиск
цитат, правила анализатора, обработка ошибок и повторов у каждого провайдера, весь конвейер,
отчёт и CLI. CI запускает их на Python 3.10, 3.12 и 3.13.

## Ограничения

* Сканированные PDF без текстового слоя нужно предварительно распознать (OCR).
* Качество проверки зависит от модели: малые локальные модели находят заметно меньше дефектов.
* Ответы модели недетерминированы; для повторяемости используйте кэш (включён по умолчанию).
* Провайдер `claude-cli` расходует лимиты подписки Claude Code того, кто запускает агента.
